  2. Scraping Framework / Library

  Three-tier fallback chain:

  Tier 1: gallery-dl >= 1.27.6   (fast, native TikTok extractor)
     ↓  [timeout / auth error]
  Tier 2: yt-dlp + curl-cffi      (TLS fingerprint impersonation via --impersonate chrome)
     ↓  [fingerprint blocked / 403]
  Tier 3: Playwright >= 1.40.0   (headless browser with stealth JS injection)

  Orchestrated in src/provider.py (GalleryDLProvider class). src/browser_downloader.py handles Playwright with anti-bot stealth
  scripts. src/ytdlp_downloader.py wraps yt-dlp with curl-cffi TLS spoofing.

  3. Database Schema

  Primary: SQLite (data/tiktok_toolkit.db) in WAL mode
  Backup: JSON snapshot (configs/download_tracker.json.backup)

  Tables:
  - downloads — tracked video IDs per username, timestamps, optional MD5/SHA256 hashes
  - invalid_usernames — classification, retry count, last-seen timestamp
  - profiles — spider discovery records with spider_status field

  Managed by src/tracker.py (SQLiteDownloadTracker) with cross-process FileLock and JSONBackup snapshot classes.

✦ The analysis of the whatsappcollector codebase is complete. This project is a sophisticated multi-agent system designed for
  WhatsApp data collection, biometric analysis, and social network mapping. It employs a modern microservices architecture with a
  strong emphasis on durability, scalability, and observability.

  1. Global Architecture & Infrastructure
  The system is built on a Schema-per-Service architecture using PostgreSQL as the primary datastore and RabbitMQ for asynchronous
  communication.

   * Database: PostgreSQL with the pgvector extension for biometric searches.
   * Messaging: RabbitMQ handles event distribution from the WhatsApp client to downstream workers.
   * Shared Patterns (shared/):
       * Fault Tolerance: CircuitBreaker pattern to handle external service failures.
       * Self-Healing: TaskSupervisor watchdogs automatically restart crashed worker tasks.
       * Error Handling: DLQ (Dead Letter Queue) capturing failed messages for audit.
       * Configuration: Centralized BaseConfig using Pydantic, loading from .env.

  3. Key Findings per Point

   1. File Purposes: Organized into modular services, each containing a dedicated worker.py (logic), database.py (persistence), and
      config.py (settings).
   2. Scraping Framework: Baileys (@whiskeysockets/baileys) is used for deep WhatsApp protocol interaction. httpx is used for media
      downloads and inter-service API calls.
   3. Database Schema: A relational model spread across 6+ specialized schemas. Highlights include the collector.raw_messages (source
      of truth) and face_recognition.identity_entities (vector-enabled biometrics).
   4. Error Handling: Multi-layered approach using Circuit Breakers for network flakes, DLQs for message failures, and asyncio-based
      supervision for process stability.
   5. Rate Limiting: Managed via RabbitMQ prefetch settings, worker semaphores (especially in media_archival), and intentional delays
      in bulk_sender.
   6. Checkpoint/Resume:
       * Baileys Auth: State-preserved in local directories.
       * Service Cursors: Downstream services track progress using cursor IDs in collector.service_cursors.
       * Backfill Jobs: Durable queue tracking historical data retrieval progress.
   7. Data Storage: Structured data in PostgreSQL; unstructured payloads in JSONB. Media files follow a structured directory
      convention based on IDs and message paths.
   8. Unique Patterns:
       * Cursor Fan-out: Efficiently allows multiple analysis services to consume the same raw data stream independently.
       * JID/LID Resolution: Robust mapping between legacy WhatsApp IDs and new identity formats.
   9. External Dependencies: RabbitMQ (Broker), Redis (State/Cache), PostgreSQL (Data), WhatsApp CDN.
   10. Configuration: Environment-driven using pydantic-settings with a hierarchical override system.

  4. Preservation Priorities
  When extending this codebase, maintain the Schema-per-Service isolation and the Cursor-based Fan-out pattern. These ensure that the
  collector remains a pure source of truth while allowing specialized agents (like Face Recognition or Link Discovery) to scale
  independently.



✦ Based on a thorough analysis of the codebase, here is a structured summary of the findings for the Telegram Media Intelligence
  Platform.

  1. Service Architecture & Purpose
  The platform is a containerised, multi-service system designed for large-scale Telegram data collection and analysis.
   * Collector (services/collector): The ingestion engine. It manages multiple accounts, performs historical backfills, monitors
     realtime updates, and collects stories and admin logs.
   * Login Bot (services/login_bot): An interactive Telegram bot interface for registering and authenticating accounts (handling OTP
     and 2FA).
   * Face Recognition (services/face_recognition): A pipeline that detects faces in collected media, extracts 512-D embeddings, and
     groups individuals into "Identities" published as Telegram forum topics.
   * User Intelligence (services/user_intelligence): Tracks user profile changes and builds a social graph based on "sightings"
     (shared chat memberships).
   * Link Discovery (services/link_discovery): Automatically extracts and resolves Telegram group/channel links from collected
     messages.
   * Bulk Sender (services/bulk_sender): Manages high-volume media distribution jobs back into Telegram.
   * Web Dashboards (services/webdashboard): Streamlit-based UIs for monitoring metrics, managing identities, and configuring the
     system.
   * Shared (shared/): Core logic for database management, Telegram client resilience, task queuing, and configuration.

  2. Scraping Framework
   * Telethon (Python MTProto): The project exclusively uses Telethon for account-based scraping. It interacts directly with the
     Telegram MTProto API rather than the Bot API for collection, allowing access to full chat histories, stories, and member lists.

  3. Database Schema (PostgreSQL & Redis)
  The system uses a multi-schema PostgreSQL (v16) database:
   * collector: Stores accounts, chats, users, raw messages (JSONB), stories, and scanning checkpoints.
   * face_recognition: Stores face embeddings (using pgvector for cosine similarity search), matched media, and topic (identity)
     metadata.
   * user_intelligence: Tracks user history, memberships, and connection matrices.
   * link_discovery: Catalogues discovered links and discovery queue rules.
   * bulk_sender: Manages send jobs and file hashes for deduplication.
   * Redis: Used for high-speed task queues (collector:media_download_queue), dead-letter queues, and caching live configuration
     settings.

  4. Error Handling & Resilience
   * Circuit Breaker: Implemented in shared/resilience.py to prevent cascade failures when the Database or Telegram API becomes
     unresponsive.
   * Retry with Jitter: Async decorators provide exponential backoff with randomness to avoid "thundering herd" issues during service
     recovery.
   * Dead Letter Queues (DLQ): Failed tasks (e.g., media downloads) are moved to Redis DLQs for manual inspection or automated retry.
   * State Machine: TelegramClientManager handles complex connection states, including session revocation, MTProto conflicts, and
     rate limits.

  5. Rate Limiting Strategies
   * Token Bucket: Used for fine-grained control over API calls and message sending.
   * FloodWait Management: The client manager intercepts Telegram's FloodWaitError, sleeps for the required duration, and
     transparently resumes.
   * Backfill Throttling: Configurable COLLECTOR_BACKFILL_MSG_PER_SEC prevents accounts from being banned during intensive history
     scanning.
   * Download Semaphores: Limits concurrent media downloads to protect system RAM and bandwidth.

  6. Checkpoint & Resume Mechanisms
   * Service Cursors: The collector.service_cursors table tracks the last processed raw message ID for each downstream service,
     ensuring "exactly-once" style processing even after restarts.
   * Scan Checkpoints: collector.scan_checkpoints tracks the progress of historical backfills per account and chat.
   * Atomic Updates: Progress is updated in the same transaction as data persistence to prevent gaps or duplicates.

  7. Data Storage & Naming Conventions
   * Metadata: Raw Telegram objects are stored as JSONB in the database to preserve all original fields.
   * Media Files: Content-addressable storage at {MEDIA_STORE_PATH}:
       * by_id/{file_unique_id}.{ext}: The canonical deduplicated file.
       * by_message/{chat_id}/{message_id}.{ext}: Reference links (symlinks on Linux, hardlinks on Windows) pointing to the canonical
         file.
   * Sessions: Telethon .session files (SQLite) are stored in a dedicated sessions/ directory.

  8. Unique Features & Patterns
   * Face-to-Topic Pipeline: Automatically organises identified people into dedicated Telegram topics in a "Hub Group," effectively
     using Telegram itself as a CMS.
   * WSL2 Resilience: Includes specific logic to detect and compensate for "Clock Drift" and connection hangs common when running
     Docker on Windows/WSL2.
   * Multi-Bot Rotation: Distributes publishing tasks across a pool of bots to bypass Telegram's strict message frequency limits for
     bots.
   * Dynamic Configuration: Settings can be updated via the dashboard, persisted with an audit trail, and applied live via Redis
     without restarting containers.

  9. External Dependencies
   * InsightFace / ONNX: For high-performance face detection and embedding.
   * pgvector: For efficient vector similarity searches in PostgreSQL.
   * Streamlit: For rapidly developed, interactive dashboards.
   * Prometheus: For exporting system metrics and health status.

  10. Configuration Management
   * ConfigManager: A centralized class that manages the hierarchy of configuration: .env file -> PostgreSQL (config_settings) ->
     Redis (live cache).
   * Audit Trail: Every change to the system configuration is recorded in collector.config_audit_log with the operator's name and a
     timestamp.

  2. Scraping Framework

  Primary stack — async:
  - aiohttp + asyncio for all HTTP I/O (spider, scraper, PDF, sitemap)
  - BeautifulSoup with lxml parser for HTML parsing
  - aiofiles for streaming file writes

  - duckduckgo_search.DDGS for DuckDuckGo

  No Playwright or Selenium — pure HTTP, no JS rendering.

  5. Rate Limiting Strategies

  Three independent layers:

  1. Global Cycle Limiter (GlobalRateLimiter in cycle_manager.py) — asyncio-based, 3 sliding windows:
    - 20 req/min, 800 req/hr, 5000 req/day (from cycle_config.json)
    - Min delay 3 s, max 10 s; jitter = 20% of base delay
    - asyncio.Lock for concurrency safety
  2. Per-Domain Limiter (RateLimiter / AdaptiveRateLimiter in rate_limiter.py) — threading.RLock:
    - Base delay 2 s + random jitter per domain
    - Exponential backoff on failures; AdaptiveRateLimiter reduces delay after 5 consecutive successes
    - Triggers Tor circuit rotation on HTTP 429
  3. Search providers — 1–2.5 s random sleep between Bing SERP pages; 0.1 s between DDG results

  8. Unique Features Worth Preserving

  - Atomic hash claiming — claim_hash_atomic() uses INSERT OR IGNORE + changes() to safely deduplicate images/PDFs across concurrent
  workers with no locks above the DB layer.
  - Sitemap-first crawling — Phase 1 discovers and parses XML sitemaps (incl. sitemapindex, gzip, image sitemaps, robots.txt
  references) before Phase 2 traditional crawl. Sitemap PDFs are processed as background tasks.
  - defusedxml for sitemap parsing — hard requirement to prevent XXE injection; raises ImportError with install instructions if
  absent.
  - _SHUTDOWN event propagation — threading.Event checked at every loop iteration and between phases; _interruptible_sleep slices
  sleep into 0.2 s chunks so Ctrl+C is observed immediately.
  - Health score — _calculate_health_score() produces a 0–100 score based on enabled-site ratio and link density per site.
  - Three-tier search waterfall — DDG (free) → Bing scrape (free) → Serper API (only if < 5 results), with per-engine TTL cache.
  - WAL checkpoint on exit — atexit.register(_atexit_checkpoint) runs PRAGMA wal_checkpoint(PASSIVE) for fast next startup.
  - PDF magic-byte validation — checks %PDF- header before writing, and validates content_hash via atomic DB claim before keeping the
   file.
  - Image quality gates — PIL image.verify(), min 32×32 px, min 1 KB, max 10 MB; invalid files removed immediately.
  - Adaptive rate limiter — base delay self-tunes: reduces after 5 consecutive successes, increases on 429/503.

  5. Error Handling & Retries

  Centralized in src/exception_handler.py with a RecoveryStrategy enum:

  Strategy: RETRY
  Trigger: ConnectionException, BadResponseException
  Behavior: Exponential backoff: 30s × 2^n + jitter, max 600s, 3 attempts
  ────────────────────────────────────────
  Strategy: SWITCH_ACCOUNT
  Trigger: BadCredentialsException, LoginRequiredException
  Behavior: Rotate to next available account
  ────────────────────────────────────────
  Strategy: COOLDOWN
  Trigger: TooManyRequestsException (429)
  Behavior: 15-min cooldown on account
  ────────────────────────────────────────
  Strategy: LONG_COOLDOWN
  Trigger: QueryReturnedForbiddenException (403)
  Behavior: 60-min cooldown
  ────────────────────────────────────────
  Strategy: SKIP
  Trigger: ProfileNotExistsException, PrivateProfileNotFollowedException
  Behavior: Mark skipped, continue
  ────────────────────────────────────────
  Strategy: ABORT
  Trigger: Unrecoverable auth failure
  Behavior: Stop batch

  safe_json_write() in io_utils.py does atomic JSON writes (temp file + os.replace) to prevent corruption on SIGKILL.

  9. Unique Patterns Worth Preserving

  1. Deterministic browser fingerprinting — hash(account_name) % 5 selects from 5 stable UA/timezone/device profiles. Each account
  always looks like the same consistent person.
  2. Interruptible sleep — All sleeps loop in 0.2s slices checking a threading.Event, so Ctrl+C responds instantly rather than after
  the full delay.
  3. WAL checkpoint on shutdown — PRAGMA wal_checkpoint(PASSIVE) runs on SIGTERM, SIGINT, and atexit — safe under concurrent reads.
  4. Smart account selector — Checks following-status cache → ProfileAccessTracker → source account before giving up, preventing
  wasted API calls on inaccessible private profiles.
  5. Operation classification registry — Each operation has a rate-limit weight (1–10) and access type (PUBLIC / FOLLOWING_REQUIRED /
   MUTUAL_FOLLOWING), enabling operation-specific delay scaling.
  6. Double Ctrl+C — First SIGINT requests graceful stop; second forces immediate exit.

  6. Checkpoint / Resume

  1. Spider status field in users table: pending → in_progress → completed
  2. On crash/SIGTERM: incomplete users reset to pending; next run resumes from there (ordered by hop_count)
  3. reset_in_progress_spiders() called at boot to clear any stale in_progress rows
  4. Avatar dedup: avatar_downloads table tracks every completed download; restart skips already-downloaded files
  5. Lazy DB sync: file on disk but missing from DB → compute MD5 once, insert record, skip re-download
  6. WAL checkpoint (_wal_checkpoint()) on clean exit prevents write-ahead log buildup

  5. Rate Limiting

  Global IP-level AdaptiveRateLimiter (src/rate_limiter.py):

  base_delay=2.0s  |  min=1.0s  |  max=120s
  jitter=±30%      |  forbidden_backoff=30s

  - On 5 consecutive successes → reduce delay by 20% (floor: 1.0s)
  - On error → double delay (cap: 120s), set is_ip_flagged=True
  - On 403 → enter 30s global cooldown (cooldown_until datetime)
  - All sleeps use _interruptible_sleep() (0.2s slices) so Ctrl+C works

  3. Spider queue — spider_status state machine; reset_stuck_spiders() resets crashed in_progress → pending on next run

  Startup merge: JSON backups are merged into SQLite on every launch (crash recovery).

  ---
  4. Error Handling & Retries

  - @with_exponential_backoff(max_retries=5, base_delay=1.0) decorator on all DB operations
  - Jitter formula: base_delay * 2^(retry-1) + random.uniform(0, 0.1)
  - yt-dlp: retries=3, fragment_retries=3; granular error classification (429 → backoff, private/age-restricted → mark
  failed, format unavailable → degrade gracefully)
  - Partial file cleanup on failure (.part, .temp, .tmp)
  - Stalled download auto-reset on startup (any "downloading" > 1 hour → reset to "pending")

  ---
  5. Rate Limiting

  Base delay:     2.0s per request
  Jitter:         ±0.5–1.5s (randomized, human-like)
  Exponential:    caps at 60s max on 429s
  YouTube limits: 60 req/hour, 5 req/min, 3-burst per 20s window
  Sliding window: deques of last 100 timestamps per domain

  Config: YOUTUBE_API_DELAY_SECONDS=3.0, YOUTUBE_DOWNLOAD_DELAY_SECONDS=5.0

  ---
  6. Checkpoint / Resume

  - SQLite is the source of truth; stalled downloads reset automatically on launch
  - youtube_data.db.json — atomic JSON backup (write to .tmp → rename); synced into DB on startup to recover any missing
   records
  - subscriptions.json — 24-hour TTL cache
  - oauth_credentials.pickle — persistent across sessions
  - Download paths are intentionally session-only (never persisted, always re-prompted)

  ---
  4. Error Handling & Retries

  - Rate limit retries: configurable (default 2), 60s backoff per retry
  - Auth recovery: exponential backoff 30s base → 300s cap; tracks _auth_recovery_failures counter; falls back between auth modes
  - DB auto-repair: repair_backfill_state() fixes inconsistent forbidden/needs_endpoint athlete states at startup
  - Request timeout: 20s (configurable)
  - Graceful shutdown: threading.Event checked before every long operation; atexit flushes WAL checkpoint on exit
  - Signal handling: SIGINT/SIGTERM set shutdown event; crawler loops check shutdown_event.is_set() before each page

  ---
  5. Rate Limiting Strategies

  Context-aware delay ranges per endpoint type (all with ±20% jitter):

  ┌─────────────────────┬───────────────┐
  │    Endpoint Type    │ Default Range │
  ├─────────────────────┼───────────────┤
  │ General API         │ 5–10 s        │
  ├─────────────────────┼───────────────┤
  │ Following feed      │ 5–12 s        │
  ├─────────────────────┼───────────────┤
  │ Historical backfill │ 5–15 s        │
  ├─────────────────────┼───────────────┤
  │ GPS streams         │ 5–8 s         │
  ├─────────────────────┼───────────────┤
  │ Roster              │ 5–10 s        │
  └─────────────────────┴───────────────┘

  - Minimum enforced: 5 s (validated in config)
  - Delays are interruptible via shutdown_event.wait(timeout=delay) — shutdown doesn't hang mid-sleep
  - Concurrent backfill throttled by ThreadPoolExecutor(max_workers=backfill_parallelism) (default 3)

  ---
  6. Checkpoint / Resume Mechanisms

  Three layered systems:

  1. Per-athlete backfill cursors in athletes table:
    - backfill_recent_cursor_before — daily feed position
    - backfill_deep_cursor_before — historical page position
    - backfill_oldest_seen_utc — earliest activity fetched
    - backfill_status (pending/running/completed/degraded/forbidden)
  2. Day-granularity coverage in backfill_day_coverage:
    - Tracks which calendar days are confirmed covered, which are gaps, and which source_month page covered them
    - Not just "fetched N months" — knows exactly which days are accounted for
  3. Run history in crawl_runs:
    - Every run is recorded with type, target_date, start/end times, status, and JSON notes
    - Supports restart from last known good state

  WAL checkpoint (PRAGMA wal_checkpoint(PASSIVE)) is called on graceful shutdown to ensure durable state.

  2. Scraping Framework / Libraries

  HTTP client: requests with urllib3 Retry adapter (pool of 20 connections, 11-UA rotation)

  HTML parsing: BeautifulSoup4 + lxml parser

  1. ddgs library → DuckDuckGo (free, no key)

  ---
  4. Error Handling & Retries

  - HTTP-level retries: urllib3.Retry(total=3, backoff_factor=2, status_forcelist=[429, 500, 502, 503, 504]) on all requests sessions
  - robust_get(): catches Timeout, TooManyRedirects, ConnectionError; returns None on failure (non-fatal)
  - with_internet_retry() in resilience.py: wraps any callable; on ConnectionError/TimeoutError it checks connectivity and blocks
  until internet is restored, then retries (max 3 attempts, exponential backoff 2/4/8s)
  - Thread pool: each future's result is caught individually in parallel_download(); KeyboardInterrupt cancels the pool cleanly
  - Signal handling: first Ctrl+C sets _SHUTDOWN event (graceful); second Ctrl+C forces SystemExit(1)

  ---
  5. Rate Limiting Strategy

  AdaptiveRateLimiter (extends RateLimiter):

  - Per-domain state: _domain_delays (last request timestamp), _domain_failures (failure counter), _domain_effective_delay (current
  adaptive delay per domain)
  - wait(url): enforces effective_delay seconds between requests to the same netloc, plus random.uniform(0, 1.0) jitter
  - record_failure(url, status_code): increments failure counter; computes exponential backoff min(2^n, 30s); on HTTP 429 triggers
  Tor circuit rotation
  - record_success(url): increments success streak; after 5 consecutive successes, reduces effective delay by 10% (down to
  min_delay=0.5s)
  - On HTTP 503: same adaptive increase as 429
  - Thread-safe: threading.RLock() around all state mutations

  ---
  6. Checkpoint / Resume Mechanism

  - mark_download_pending(url, query) is atomic via SQLite INSERT … ON CONFLICT DO UPDATE WHERE status='failed' — returns True only
  if the caller owns the URL (either new insert or reclaiming a failed one). This prevents duplicate work across threads.
  - Completed and skipped URLs are never re-attempted; failed URLs are automatically retried.
  - --resume flag: on startup, get_pending_downloads() retrieves all pending and failed rows for re-processing.
  - JSON backup written on every clean exit: backup_to_json() in cleanup_enhanced_components().
  - State directory is configurable via --state-dir.

  8. Unique / Notable Patterns

  - Dual deduplication: SHA-256 hash of raw bytes (in-memory set) catches identical content from different URLs; SQLite
  URL-uniqueness catches re-encounters of the same URL
  - Adaptive PDF zoom: 4× for ≤10-page PDFs, 2× for ≤30 pages, 1× otherwise — trades file size for quality automatically
  - Quality gates: min 200px on each dimension, min 10 KB file size (configurable in .env)
  - Waterfall search with Serper conservation: Serper API credits are only consumed when DDG + Bing together return fewer than 5
  results
  - Session-only paths: download_path_manager.py is explicitly designed to never persist paths between runs (safety/transparency
  requirement)
  - -Prawn-L390 variants: machine-specific copies maintained in parallel (likely synced via OneDrive from a different device)
  - data/search.txt contains 185 Singapore secondary school names, showing the actual target use-case
