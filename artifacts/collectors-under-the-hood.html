unifiedcollector — collectors under the hood

How each of the 16 collector services actually works — protocol, data flow, tables written, and failure modes. Snapshot 2026-09-19; source of truth C:\unifiedcollector\docker\docker-compose.yml.

Visual overview

Each row is one collector's end-to-end path. All arrows converge on the same Postgres cluster (unifiedcollector_postgres). RabbitMQ is used only by WhatsApp; Chrome CDP is used only by the browser-scraped platforms; everything else goes direct API -> asyncpg pool.

collector_whatsapp src/collectors/whatsapp/

Purpose

Ingest WhatsApp messages, contacts, groups, sessions from two paired phone accounts through a Baileys bridge fleet. Preserves the underlying network graph and history without touching the phone.

How it works

Two Node/Baileys sidecars (wa_bridge_1, wa_bridge_2) run the WhatsApp Multi-Device protocol against a scanned session each. They emit domain events (messages.upsert, contacts.set, groups.update, session) onto four RabbitMQ queues. collector_whatsapp consumes with aio_pika and writes via asyncpg.

Two write paths (opt-in by env)

PathEnvBehavior
Sprint 4 batchingWA_STAGING_ENABLED=0 defaultBuffer up to WA_CONTACT_BATCH_MAX events, flush via array-parameterised UPSERT with COALESCE merge on name/pushname/phone_number + OR-merge on is_business.
Sprint 5 stagingWA_STAGING_ENABLED=1asyncpg.copy_records_to_table into UNLOGGED wa_staging_contacts; scheduler-side WhatsappStagingMergeHandler drains it every 5s.

Tables written

  • whatsapp_users, whatsapp_messages, whatsapp_chats, whatsapp_lid_map, whatsapp_user_changes
  • wa_staging_contacts (UNLOGGED, drained by scheduler)
  • media_items (audio disabled by default)

Failure modes

  • bridge_unpaired session revoked, needs manual QR scan on phone
  • rabbitmq_unavailable falls back to HTTP polling
  • poison_row batch upsert fails, falls back per-event to isolate the offending payload

collector_telegram src/collectors/telegram/

Purpose

Real-time and historical Telegram capture across four seed accounts using Telethon (MTProto). Highest-volume live source (~78 msg/15 min).

How it works

One TelegramClient per account inside a single asyncio loop. Accounts supplied via TELEGRAM_SPIDER_ACCOUNTS. Split into mixins:

realtime
event-driven capture through events.NewMessage
backfill
rate-limited paging of historical messages per chat
media
downloads via iter_download, deduped by SHA-256
helpers
MTProto entity resolution, invite links, admin events
parse
message text -> mentions, URLs, locations, replies

Tables written

  • telegram_messages, telegram_users, telegram_user_accounts, telegram_user_changes
  • telegram_admin_events, telegram_chat_members, telegram_pinned_events, telegram_poll_votes, telegram_invite_visits
  • telegram_message_mentions, telegram_message_locations, telegram_deletion_index
  • telegram_spider_queue — chat discovery frontier

Failure modes

  • flood_wait Telegram rate-limit; sleep + resume
  • session_migrate MTProto DC hop; Telethon reconnects
  • auth_key_unregistered session revoked; re-auth

collector_instagram src/collectors/instagram/

Purpose

Ingest Instagram profiles, posts, media using the user's logged-in Chrome session — no username/password stored in the collector.

How it works

Two hemispheres:

  1. Extension side (host): MV3 Chrome extension v1.23.103 injected into instagram.com. Content script scrapes /explore/, feed, profile pages and POSTs canonical events to ig_ingest :8765. CDP on 127.0.0.1:9336 lets host tooling audit/repair tabs without disturbing the user's session.
  2. Container side: python -m src.main worker --source instagram. Handles backend calls that don't need the browser (public profile lookups, graph_ql fallback).

Tables written

  • instagram_profiles, instagram_tls_state_table, instagram_user_changes
  • media_items (source=instagram, partitioned)
  • browser_ingest_events — raw extension deliveries

Failure modes

  • http_429 IG rate-limit; content script backs off, tab reload path
  • removed_post page shell only; maintenance reopens tab to /explore/
  • cdp_unavailable Chrome launched without --remote-debugging-port=9336; repair via scripts/start-scraper-chrome-cdp.ps1

collector_instagram_dm src/collectors/instagram_dm/

Purpose

DM-specific IG capture. Runs in its own container so the DM code path is rate-limited independently and aggressive DM anti-bot can't take down the whole IG collector.

How it works

Same content-script pattern, scoped to DM inbox route. Uses the dm_sample lane in ig_ingest at concurrency 1 — deliberately slow.

Tables written

  • dm_hook_heartbeat, dm_probe_log

collector_tiktok src/collectors/tiktok/

Purpose

TikTok profile + media capture through the extension mechanism.

How it works

Content script scrapes tiktok.com/following + profile URLs, POSTs events. Container side hosts backfill via TikTok's __NEXT_DATA__ hydration payloads. Media downloader uses gallery-dl when the page's JS isn't needed.

Tables written

  • tiktok_users, tiktok_user_changes
  • tiktok_dm, tiktok_dm_media_url, tiktok_browser_media_diagnostics
  • media_items (source=tiktok)

Failure modes

  • rate_limit_events access pressure; queued action
  • browser_capture_stalled dashboard flag; usually clears next tick

Purpose

Ingest Lemon8 topic feeds + profile metadata for tracked handles. Backend-primary; the extension is an optional secondary probe.

How it works

collector_beeper src/collectors/beeper/

Purpose

Beeper Cloud is a Matrix-based multi-network chat aggregator. This collector shadow-mirrors messages from any network Beeper is bridging (Signal, Slack, iMessage, SMS, etc.) for cross-platform identity resolution.

How it works

Matrix client SDK against Beeper Cloud homeserver (chat.beeper.com). Ingest is event-driven via /sync long-poll. Messages are shadowed — Beeper's bridge did the network-specific decoding.

Tables written

collector_website src/collectors/website/

Purpose

Full-page snapshots + text extraction of arbitrary URLs added to a target list. Feeds link discovery from other collectors (e.g. a link seen in a Telegram message can be seeded here for capture).

collector_spiderfoot docker/spiderfoot/

Purpose

Bounded, allowlist-gated SpiderFoot 4.0 recon. Separate slim image because it has a distinct dependency set and we want it blast-radius-isolated.

How it works

Fed by recon_targets rows the analyzer marks as SpiderFoot-scope. Each run scoped by allowlisted modules (RECON_USERNAME_MODULES=maigret default routes username targets through maigret's HTTP-only fast path). Emits observations with SHA-256 value_hash unique index so re-runs dedupe.

ig_ingest src/ig_ingest/ port 8765

Purpose

HTTP endpoint the Chrome extension POSTs into. Absorbs the burstiness of seven browser platforms hitting the API at once, then serializes writes to Postgres.

How it works

FastAPI service with four bounded concurrency lanes:

heartbeat
16 — cheap presence pings
write
4 — profile/post writes
revisit
2 — profile/media revisits
dm_sample
1 — deliberately slow DM sampling

Every accepted request lands as a row in browser_ingest_events; the write lane peels those into typed platform tables (instagram_profiles, tiktok_users, threads_posts, facebook_posts, x_profiles, ...).

realtime_feed src/realtime/

Purpose

Fan-out of just-ingested media events to the operator's Telegram feed. New target post lands in media_items, feed publishes a notification with thumbnail + link within seconds.

How it works

Postgres LISTEN/NOTIFY on a media-inserted channel. Delivery ledger (realtime_media_deliveries) so duplicates and retries are auditable rather than dropped. Poster-only video thumbnails are skipped by default to avoid flooding chat.

onboard_bot src/bots/onboard_bot.py

Purpose

Operator-facing Telegram bot. Adds new tracked identities (usernames, phone numbers, emails) to tracked_entities, sends periodic system digests, and receives 2-button merge decisions from the analyzer.

How it works

Long-poll getUpdates against the collector bot token. Runs as a single asyncio task in the scheduler process — merged from its own container to save a slot.

collector src/main.py worker --all

Purpose

The historical main worker. Kept as an idle safety-net + canonical image builder. All sources are DISABLED here via COLLECTOR_DISABLED_SOURCES; each real source runs in its own dedicated container to isolate memory + subprocess reaping.

Re-enable a source in this container only if you also remove its dedicated container.

Supporting servicesnot sources but part of the flow

watchdog

Wall-clock health monitor. Reads source_health + collection_runs and re-launches stuck collectors via the docker socket. Escalates via Telegram after N failed self-heals.

scheduler

Two loops: DB-driven collection_schedules tick (per-source cadence) and periodic-handler registry (13 handlers including wa_staging_merge, recon_seed, phone_intel, watchdog_stale_alert, ...). Handlers dispatch concurrently via asyncio.gather(return_exceptions=True) (commit bf4a0f55) so a slow one no longer starves the tail.

browser_cookie_vault

HTTP service on :8790 that owns the cookie backup/restore state machine against the managed Chrome CDP profile. Vault snapshots survive a Chrome profile rebuild.

dashboard

Read-mostly FastAPI web UI. 110 routes. Feeds the operator's status page + serves /health for k8s-style probes and the watchdog's freshness gates.

postgres / rabbitmq / redis

Backing stores. Postgres is the source of truth for every collector. RabbitMQ is used only by the WhatsApp bridge fleet. Redis is used for per-source cursor + rate-limit state + inter-worker locks.

Cross-cutting concerns

Database pool

Every collector uses asyncpg.create_pool(max_size=10, command_timeout=300) with idle_in_transaction_session_timeout=5min baked in. That timeout was added after a Sep-07 audit found the analyzer's build_timeline was leaking IIT sessions during long cross-pool executemany batches.

Health surface

Every source writes to source_health (status, last_success_at, last_error, crash_count). Watchdog reads this + collection_runs and treats a source as stale when last_success_at exceeds a per-source freshness window.

Media pipeline

All collectors that download media write into media_items (partitioned by source) with a SHA-256 unique constraint so cross-source dedup is automatic. Vault artifacts land on Z: at Z:\unifiedcollector\media.

Rate limiting

rate_limit_events table + collection_action_queue capture per-source pressure so the scheduler can back off automatically and surface durable operator actions instead of spinning.

DLQ

dead_letter_queue holds messages that failed processing after N retries. Read by the DLQ consumer + presented in the dashboard. Cleaned up manually or via retention.
